## 2. Purpose

This playbook defines the L1 analyst triage procedures for network intrusion incidents. The L1 analyst is the first responder to network-based alerts and plays a critical role in determining whether an alert represents a genuine security incident, assessing initial severity, and escalating to L2 analysts in a timely and structured manner.

Network intrusion triage is inherently complex because many alerts generated by IDS/IPS systems, firewalls, and SIEM correlation rules represent false positives or benign network activity. However, delays in identifying genuine intrusion activity can allow attackers to deepen their foothold, move laterally across the network, and cause significant operational and data-related impact. L1 analysts must therefore apply a structured and disciplined approach to every network alert to ensure nothing is missed.

This document provides:

- Step-by-step L1 triage procedures for network intrusion alerts
- Alert source and validation guidance
- False positive identification criteria
- Initial severity assessment guidance
- Escalation criteria and escalation process
- Documentation requirements
- Communication procedures
- Tool usage guidance during triage

---

## 3. Scope

This playbook applies to all network intrusion alerts received by L1 analysts from the following sources:

- IDS/IPS platforms
- Firewall alert queues
- SIEM correlation rules
- NDR platform alerts
- NetFlow anomaly detection
- DNS security monitoring
- Proxy alerts
- VPN anomaly alerts
- Threat intelligence feed matches on network traffic
- MSSP client network monitoring alerts

---

## 4. L1 Analyst Responsibilities

The L1 analyst is responsible for:

- Monitoring the alert queue continuously during shift
- Acknowledging and triaging all network intrusion alerts within SLA
- Performing initial validation of alerts
- Classifying alerts as true positive, false positive, or requires further investigation
- Assigning initial severity classification
- Creating incident tickets for confirmed or suspected intrusions
- Escalating to L2 analysts according to defined criteria
- Documenting all triage steps in the ticketing system
- Communicating status to SOC Lead when required
- Performing shift handover for open triage cases

L1 analysts must not attempt deep investigation beyond initial triage. Any alert requiring packet-level analysis, advanced log correlation, or forensic examination must be escalated to L2 immediately.

## 5. Alert Sources and Initial Validation

### 5.1 IDS/IPS Alerts

IDS and IPS platforms generate the highest volume of network security alerts. Many IDS/IPS alerts are false positives resulting from poorly tuned signatures or legitimate traffic matching attack patterns. L1 analysts must validate IDS/IPS alerts before escalation.

Initial validation steps for IDS/IPS alerts include:

- Review the alert signature name and category
- Identify source IP address and destination IP address
- Determine whether source IP is internal or external
- Check whether destination asset is known and classified
- Review the alert priority assigned by the IDS/IPS platform
- Check whether the same source IP has triggered multiple alerts
- Verify whether the alert signature has a known high false positive rate
- Cross-reference source IP against threat intelligence feeds
- Review recent SIEM alerts involving the same source or destination

---

### 5.2 Firewall Alerts

Firewall alerts may indicate blocked intrusion attempts, policy violations, or anomalous traffic patterns.

Initial validation steps for firewall alerts include:

- Review the firewall rule that triggered the alert
- Identify source and destination addresses and ports
- Determine whether traffic was allowed or blocked
- Assess whether the traffic pattern is unusual for the source asset
- Review volume and frequency of the traffic
- Check whether the source IP has triggered previous firewall alerts
- Determine whether the destination port is associated with known attack techniques

---

### 5.3 SIEM Correlation Alerts

SIEM correlation rules aggregate multiple events to identify complex attack patterns. These alerts often represent higher-confidence indicators of intrusion activity.

Initial validation steps for SIEM correlation alerts include:

- Review the correlation rule logic and triggered conditions
- Identify all contributing events in the alert
- Verify timestamps and event sequence
- Assess whether the pattern matches expected attacker behavior
- Determine affected assets and their classification
- Check whether correlated events span multiple detection sources

---

### 5.4 Threat Intelligence Feed Matches

Alerts triggered by matches against threat intelligence feeds indicate that network traffic has been observed communicating with known malicious infrastructure.

Initial validation steps include:

- Confirm the matched indicator from the TI feed
- Identify the source internal asset initiating the communication
- Verify the indicator category such as C2, malware, botnet, or scanner
- Check indicator confidence and severity rating
- Review DNS query logs for associated domain resolution history
- Determine how long the communication has been occurring

## 6. L1 Triage Workflow

The L1 triage workflow provides a structured process for handling every network intrusion alert from receipt through escalation or closure.

---

### Step 1 – Alert Acknowledgement

Upon receiving a network intrusion alert:

- Acknowledge the alert in the SIEM or ticketing system within SLA timeframe
- Record the timestamp of alert receipt
- Record the alert source, rule name, and initial details
- Assign alert to self in the queue

SLA reference:
`00_GOVERNANCE/00.4_SLA-and-SLO/Internal-SLA-Definitions.md`

---

### Step 2 – Initial Alert Review

Review the alert details to gather initial context:

- Source IP address and hostname if available
- Destination IP address and hostname
- Protocol and port
- Alert signature or rule name
- Alert severity assigned by source tool
- Timestamp and duration
- Volume of traffic or number of events
- Geographic location of external IPs

---

### Step 3 – Asset Identification

Identify and classify the assets involved in the alert:

- Determine whether source IP is internal, external, or cloud-hosted
- Look up internal IPs in the asset register
- Determine asset criticality classification
- Identify asset owner and business function
- Check whether asset is in a sensitive network segment
- Determine whether destination asset is a critical server or workload

Asset classification significantly affects severity assignment. Alerts involving critical assets must be treated with higher urgency.

---

### Step 4 – Threat Intelligence Enrichment

Enrich external IP addresses and domains with threat intelligence:

- Query TI platform for IP reputation
- Check domain against known malicious domain lists
- Review any prior incidents involving the same IP or domain
- Check whether IP is associated with known threat actors
- Verify whether IP is a known scanner, proxy, or Tor exit node
- Record TI findings in the ticket

Reference:
`04_TOOLS-AND-TECHNOLOGY/04.4_Threat-Intelligence/TI-IoC-Handling-SOP.md`

---

### Step 5 – False Positive Assessment

Determine whether the alert is likely a false positive before proceeding with escalation.

Common false positive indicators include:

- Known vulnerability scanner IP performing authorized scans
- Internal network monitoring tools generating scan-like traffic
- Known third-party service communicating on unusual ports
- Legitimate software update traffic matching exploit signatures
- Internal penetration testing activity
- Recently added legitimate service on non-standard port
- High false positive rate signature with no corroborating evidence

If the alert is determined to be a false positive:

- Document the false positive rationale clearly in the ticket
- Close the ticket with false positive classification
- Note whether the false positive indicates a tuning opportunity
- Report recurring false positives to L2 for signature tuning

Reference:
`03_SOC-TIER-PROCEDURES/03.1_L1-Procedures/L1-False-Positive-Handling.md`

---

### Step 6 – Initial Severity Assignment

If the alert is not a false positive, assign initial severity based on the following criteria.

| Criteria | Severity |
|---|---|
| Active C2 communication confirmed | P1 |
| Critical asset involved with confirmed intrusion indicators | P1 |
| Multiple internal systems involved | P1/P2 |
| Lateral movement indicators | P1/P2 |
| External intrusion with internal access confirmed | P1 |
| Single system with suspicious outbound traffic | P2 |
| Internal scanning without confirmed compromise | P2/P3 |
| Low-confidence anomaly on non-critical asset | P3 |
| Informational alert with no active threat | P4 |

Reference:
`01_INCIDENT-CLASSIFICATION/01.1_Severity-Matrix/Severity-Classification-Guide.md`

---

### Step 7 – Ticket Creation

Create an incident ticket for all alerts that are not confirmed false positives.

Required ticket fields include:

- Alert source and rule name
- Source IP and destination IP
- Protocol and port
- Affected asset name and classification
- Initial severity assignment
- TI enrichment findings
- Timeline of events observed
- Initial triage analyst name
- Timestamp of triage activities

Reference:
`04_TOOLS-AND-TECHNOLOGY/04.3_Ticketing/Ticket-Lifecycle-SOP.md`

---

### Step 8 – Escalation Decision

Apply escalation criteria to determine whether L2 escalation is required.

#### Escalate Immediately to L2 if:

- C2 communication indicators are confirmed
- External attacker has confirmed internal access
- Lateral movement is suspected or confirmed
- Critical assets are involved
- Multiple alerts from same source in short timeframe
- Exploit traffic patterns detected
- VPN compromise indicators present
- Threat intelligence confirms malicious infrastructure

#### Continue L1 Monitoring if:

- Low-confidence anomaly with no corroborating evidence
- Single low-severity alert on non-critical asset
- Alert pending additional event correlation
- Situation is clearly within L1 handling capability

---

### Step 9 – Escalation Execution

When escalating to L2:

- Update the ticket with all triage findings
- Set ticket severity to confirmed or suspected level
- Assign ticket to L2 analyst or L2 queue
- Notify L2 analyst directly for P1 and P2 incidents
- For P1 incidents notify SOC Lead immediately
- Document escalation timestamp in ticket

Reference:
`05_ESCALATION-AND-COMMUNICATION/05.1_Escalation-Paths/L1-to-L2-Escalation.md`

## 7. P1 Alert Handling

P1 network intrusion alerts require immediate and urgent handling. When a P1 alert is received or identified during triage:

- Acknowledge and begin triage immediately regardless of queue position
- Notify SOC Lead verbally or via direct message within 5 minutes
- Do not wait for ticket completion before verbal notification
- Escalate to L2 immediately
- Assist L2 by providing all initial triage data verbally
- Initiate bridge call preparation if required by SOC Lead
- Continue monitoring for additional related alerts during escalation

Reference:
`05_ESCALATION-AND-COMMUNICATION/05.1_Escalation-Paths/Emergency-Escalation-P1.md`

## 8. Key Indicators L1 Must Look For

The following indicators represent high-priority signals during network intrusion triage. Any of these indicators should prompt immediate escalation to L2.

### 8.1 External Threat Indicators

- Traffic from known malicious IP addresses
- Communication with known C2 domains or IPs
- Traffic using Tor exit nodes or anonymous proxies
- Connections to newly registered domains
- Beaconing patterns with regular intervals
- DNS queries with high-entropy domain names
- Large outbound data transfers to external destinations

### 8.2 Internal Threat Indicators

- Internal host scanning multiple other internal hosts
- Internal host connecting to unusual internal ports
- SMB lateral movement indicators
- NTLM authentication anomalies
- Internal host generating IDS alerts targeting other internals
- Unusual authentication patterns from internal workstations

### 8.3 Protocol and Traffic Indicators

- Non-standard port usage for known protocols
- HTTP or DNS tunneling patterns
- Unusual encrypted traffic volumes
- Protocol mismatches such as HTTP on port 443
- Large DNS response payloads
- Outbound SMTP from non-mail servers

## 9. SIEM Queries for L1 Triage

L1 analysts should use the following SIEM queries to support triage activities.

### 9.1 Check Source IP Alert History

Purpose: Determine whether source IP has previously triggered alerts.

- Query: source_ip = [alert_source_ip] AND timeframe = last_30_days
- Review: Alert types, frequency, and resolution status

### 9.2 Check Destination Asset Alert History

Purpose: Determine whether destination asset has been involved in prior alerts.

- Query: destination_ip = [alert_destination_ip] AND timeframe = last_30_days
- Review: Any prior compromise indicators or investigation notes

### 9.3 Check for Related Lateral Movement

Purpose: Identify whether source IP has connected to multiple internal hosts.

- Query: source_ip = [internal_source_ip] AND destination_ip = internal_range AND event_type = connection AND timeframe = last_24_hours
- Review: Number of unique destinations and ports contacted

### 9.4 DNS Query Review

Purpose: Identify suspicious domain resolution from alert-related hosts.

- Query: source_ip = [alert_source_ip] AND event_type = dns_query AND timeframe = last_24_hours
- Review: Domain names resolved, response codes, and query frequency

### 9.5 Outbound Transfer Volume Check

Purpose: Identify potential data exfiltration from alert source.

- Query: source_ip = [alert_source_ip] AND direction = outbound AND bytes_out > threshold AND timeframe = last_24_hours
- Review: Total bytes transferred and destination addresses

## 10. Common Network Intrusion Alert Types and Triage Guidance

### 10.1 Port Scan Alert

Description: Source IP is scanning multiple ports on destination.

Triage steps:
- Determine whether source is internal or external
- Check whether source is an authorized scanner
- Assess number of ports scanned and timing
- Review whether any ports were successfully accessed
- If external source: escalate to L2 immediately
- If internal unauthorized source: escalate to L2

---

### 10.2 Brute Force Alert

Description: Multiple failed authentication attempts from single source.

Triage steps:
- Identify target service and credentials targeted
- Review number of attempts and timeframe
- Determine whether any successful authentication occurred
- Check whether source IP is known malicious
- If successful auth detected: escalate to L2 as P1/P2 immediately

---

### 10.3 Exploit Attempt Alert

Description: IDS has detected known exploit payload in network traffic.

Triage steps:
- Identify exploit signature and CVE if available
- Determine target system and whether it is vulnerable
- Review whether exploit was blocked or allowed
- Check for post-exploitation indicators
- Escalate to L2 immediately regardless of block status

---

### 10.4 Suspicious Outbound Connection

Description: Internal host connecting to external IP on unusual port or to known malicious destination.

Triage steps:
- Identify internal source host
- Query TI platform for external destination
- Review DNS logs for domain resolution
- Check data volume transferred
- If TI confirms malicious: escalate to L2 as P1/P2 immediately

---

### 10.5 Beaconing Alert

Description: Internal host making regular interval connections to same external destination.

Triage steps:
- Identify internal source host
- Measure beacon interval and consistency
- Query TI for external destination
- Review process initiating connections if EDR data available
- Escalate to L2 immediately as likely C2 indicator

---

### 10.6 DNS Tunneling Alert

Description: Unusual DNS query patterns suggesting data exfiltration or C2 via DNS.

Triage steps:
- Identify source host generating DNS queries
- Review domain names for high entropy
- Check query volume and frequency
- Compare with baseline DNS activity
- Escalate to L2 immediately

---

## 11. Documentation Requirements

Thorough documentation is essential for every network intrusion triage activity. L1 analysts must record the following in the incident ticket:

- All alert details including source, destination, protocol, and time
- Asset identification findings
- Threat intelligence enrichment results
- False positive assessment rationale if applicable
- Initial severity assignment with justification
- All SIEM queries performed and results
- Escalation details including recipient and timestamp
- Any verbal communications with SOC Lead

Documentation must be completed before shift handover for all open cases.

---

## 12. Shift Handover Requirements

At the end of each shift, L1 analysts must hand over all open network intrusion triage cases to the incoming analyst.

Handover must include:

- Open ticket list with current status
- Summary of key findings for each open case
- Pending actions required
- Active P1/P2 incidents with current status
- Any communication sent to L2 or SOC Lead
- Notable patterns observed during shift

`03_SOC-TIER-PROCEDURES/03.1_L1-Procedures/L1-Shift-Handover-Template.md`

## 13. MSSP Client Triage Considerations

For MSSP-managed clients, L1 triage must additionally:

- Identify which client environment the alert relates to
- Apply client-specific escalation thresholds if defined
- Follow client-specific SLA timelines for response
- Ensure client evidence is handled in segregated ticketing
- Notify client contact according to client escalation matrix if required
