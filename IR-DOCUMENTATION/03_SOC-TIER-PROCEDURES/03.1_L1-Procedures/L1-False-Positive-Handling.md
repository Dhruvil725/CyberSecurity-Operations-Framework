# 2. Purpose

This Standard Operating Procedure (SOP) defines the process for identifying, validating, documenting, and handling false positive alerts at the Level 1 (L1) SOC tier.

False positive handling is one of the most operationally sensitive responsibilities within a SOC because incorrect handling can lead to:

- Missed real attacks
- Alert fatigue
- Excessive escalation volume
- Analyst desensitization
- SIEM and EDR inefficiency
- SLA degradation
- Reduced confidence in detection platforms

A mature SOC must balance two critical goals:

1. Minimize unnecessary escalations
2. Never suppress genuine malicious activity

This SOP ensures:

- Structured false positive validation
- Consistent analyst decision-making
- Safe alert closure procedures
- Detection tuning feedback
- Audit-ready documentation
- Reduction of operational alert fatigue

Applies to:

- SIEM alerts

- IDS/IPS alerts

- Email security alerts
- MSSP-managed client environments

# 4. Definition of False Positive

A false positive is:

"A security alert generated by a detection mechanism where the observed activity is determined to be legitimate, expected, authorized, or non-malicious after validation."

False positives may occur because of:

- Detection rule sensitivity
- Administrative tools
- Legitimate automation
- Vulnerability scanners
- Backup activity
- Monitoring misconfiguration
- Baseline changes
- Cloud auto-scaling behavior

---

# 5. Operational Risks of Incorrect False Positive Handling (IMPORTANT)

Improper false positive handling creates major security risks.

---

## 5.1 False Negative Risk

The biggest danger is incorrectly dismissing a real attack as benign.

Examples:

| Incorrect Assumption | Actual Risk |
|---|---|
| “PowerShell is normal admin activity” | Malware execution |
| “Scanner traffic is expected” | Internal reconnaissance |
| “Cloud login is developer activity” | Compromised account |
| “DNS spikes are application related” | DNS tunneling |

---

## 5.2 Alert Fatigue Risk

High false positive volume causes:

- Analyst burnout
- Reduced attention to real threats
- Delayed triage
- Escalation hesitation
- Operational complacency

SOC Leads must monitor recurring false positive trends carefully.

# 6. False Positive Handling Workflow

| Phase | Objective |
|---|---|
| Phase 1 | Alert review |
| Phase 2 | Context validation |
| Phase 3 | Threat assessment |
| Phase 4 | False positive determination |
| Phase 5 | Documentation |
| Phase 6 | Tuning recommendation |

---

# 7. Phase 1 – Alert Review

The analyst must begin by reviewing the full alert context rather than relying only on alert title or severity.

---

## 7.1 Initial Review Requirements

| Check | Purpose |
|---|---|
| Alert source | Determine detection reliability |
| Timestamp | Correlation accuracy |
| Source host | Asset criticality |
| User account | Privilege assessment |
| Parent/child process | Behavioral validation |
| Network destination | Reputation check |
| Historical occurrences | Pattern analysis |

---

## 7.2 Immediate Escalation Conditions

The following alerts must NOT be closed as false positives without L2 review:

| Alert Type | Reason |
|---|---|
| Domain admin activity anomaly | High risk |
| Credential dumping indicators | Critical |
| Ransomware behavior | Critical |
| Data exfiltration indicators | Critical |
| Cloud admin anomaly | Critical |
| Active C2 communication | Critical |

---

# 8. Phase 2 – Context Validation

False positive determination must always include business and operational context.

---

## 8.1 Context Validation Questions

| Question | Why Important |
|---|---|
| Is the activity expected? | Business validation |
| Is the source host authorized? | Asset legitimacy |
| Is the tool approved? | Admin activity verification |
| Is the timing normal? | Behavioral anomaly detection |
| Is the user authorized? | Privilege validation |
| Has this behavior occurred before? | Baseline comparison |

---

## 8.2 Common Legitimate Activity Sources

| Source | Common Alerts Triggered |
|---|---|
| Vulnerability scanners | Port scanning |
| Backup systems | Large outbound traffic |
| IT automation | PowerShell execution |
| Cloud orchestration | API spikes |
| DevOps pipelines | Script execution |
| Security testing | IDS signatures |

---

## 8.3 Baseline Validation (IMPORTANT)

A key L1 skill is understanding normal behavior.

The analyst should compare:

- User behavior against historical baseline
- Host activity against normal patterns
- Time-of-day behavior
- Geographic login history
- Typical process execution

Example:
- PowerShell on a domain controller at 2 AM by non-admin user = suspicious
- PowerShell by SCCM server during maintenance window = likely benign

---

# 9. Phase 3 – Threat Assessment

Even if activity appears legitimate, the analyst must evaluate potential abuse scenarios.

---

## 9.1 Abuse Possibility Assessment

Ask:

| Question | Purpose |
|---|---|
| Could attacker abuse this legitimate tool? | LOLBin assessment |
| Is the account compromised? | Credential abuse check |
| Is the activity excessive? | Anomaly detection |
| Does telemetry indicate hidden malicious behavior? | Correlation analysis |

---

## 9.2 Living-Off-the-Land Awareness (IMPORTANT)

Many advanced attacks use legitimate tools.

Examples:

| Tool | Possible Abuse |
|---|---|
| PowerShell | Malware execution |
| PsExec | Lateral movement |
| WMI | Remote execution |
| certutil.exe | Malware download |
| mshta.exe | Script execution |

Do not assume legitimacy simply because the tool is legitimate.

---

# 10. Phase 4 – False Positive Determination

An alert may only be closed as false positive when:

- Context confirms legitimacy
- No malicious indicators remain
- No correlated suspicious activity exists
- Activity matches expected baseline
- Asset owner validation completed if required

---

## 10.1 False Positive Confidence Levels

| Confidence Level | Meaning |
|---|---|
| High Confidence FP | Clearly legitimate |
| Medium Confidence FP | Likely legitimate but unusual |
| Low Confidence FP | Uncertain – escalate |

---

## 10.2 Mandatory Escalation Conditions

Escalate instead of closing if:

| Condition | Action |
|---|---|
| Unusual admin activity | Escalate |
| Unknown external IP | Escalate |
| Suspicious timing | Escalate |
| Multiple correlated alerts | Escalate |
| Critical asset involved | Escalate |

When uncertain:
Escalate to L2.

---

# 11. Phase 5 – Documentation Requirements

Every false positive closure must include detailed justification.

---

## 11.1 Required Documentation

| Requirement | Example |
|---|---|
| Reason for closure | “Confirmed Nessus scan” |
| Validation source | “Validated with asset owner” |
| Historical comparison | “Matches weekly maintenance pattern” |
| Evidence reviewed | “Reviewed PowerShell command line” |
| Analyst conclusion | “No malicious indicators identified” |

---

## 11.2 Good vs Bad Documentation

GOOD:
“Alert triggered by approved Qualys scanner IP during scheduled maintenance window. Activity matches historical pattern. No additional suspicious activity observed.”

BAD:
“Looks normal.”

# 13. Special Cases (IMPORTANT)

---

## 13.1 Cloud False Positives

Cloud environments generate many legitimate anomalies due to:

- Auto-scaling
- Serverless execution
- Dynamic IP assignment
- API orchestration
- CI/CD pipelines

However:
Cloud admin anomalies should never be dismissed casually.

---

## 13.2 Threat Intelligence False Positives

Threat intelligence hits may be false positives because:

- Shared cloud infrastructure
- CDN overlap
- Reused hosting providers
- Stale IoCs

Validate:
- Context
- Timing
- Related activity
- Destination behavior

---

## 13.3 Authentication False Positives

Common authentication false positives:

| Scenario | Example |
|---|---|
| VPN reconnects | IP changes |
| Mobile roaming | Geo anomalies |
| Shared admin account | Multiple source systems |

Still validate carefully for:
- MFA status
- Timing anomalies
- Device mismatch

---

# 14. MSSP-Specific False Positive Handling

For MSSP environments:

- Validate client-specific baselines
- Follow client-approved tuning rules
- Avoid suppressing cross-client indicators
- Document client-specific exceptions
- Escalate recurring FP trends to detection engineering

---

# 15. Metrics and Quality Monitoring

SOC management should track:

| Metric | Purpose |
|---|---|
| False positive rate | Detection quality |
| Repeat FP alerts | Tuning effectiveness |
| Incorrect FP closures | Analyst quality |
| Escalation reversals | Process quality |
| Alert backlog | Operational health |

---

# 16. Common False Positive Handling Mistakes

| Mistake | Operational Risk |
|---|---|
| Closing alerts too quickly | Missed compromise |
| Assuming admin activity is safe | LOLBin abuse missed |
| Ignoring timing anomalies | Stealth attacks missed |
| Poor documentation | Audit failure |
| Not escalating uncertainty | Delayed detection |
| Suppressing alerts globally | Visibility loss |
